# Reference-driven factory: architecture proposal

This proposal extends the existing factory. It does not install a new runtime or
claim that the proposed integrations work. The source audit covered the current
workflow, factory, project controls and installer. Existing helper guarantees
remain bounded to the operations they own.

The goal is to build the full intended product with less supervision, using
references to improve judgment and execution. A dependable version can become
available for personal use while the remaining authorized work continues. Early
availability does not reduce the completion scope, fidelity or quality target.
Visual development is a central production path, alongside behavioral and
implementation work.

The [design evidence](factory-design-evidence.md) traces dependent research
questions to the mechanisms and limits behind these choices. Research and
independent reviews inform this proposal; integrated effectiveness still requires
the complete-journey qualification described below.
The [project walkthrough](factory-walkthrough.md) explains the intended experience
from an ordinary request through dependable early use and full completion.

## Build on the existing factory

Keep one journal and the native conversation as the entry point. The RDD skill
provides discovery, mechanism synthesis and reference transfer. The existing
factory supplies owned operation admission, intent lineage, resource claims,
research episodes, reconciliation and delivery records. Project controls supply
project-specific launch, observation, verification and reset operations.

| Existing foundation | Preserve | Proposed change or missing connection |
| --- | --- | --- |
| `workflow.py` task, decisions, transfers and context | Full objective, competence and character, provenance, declared impact | Property-scoped dependencies and tested evidence selection; detect omitted impacts before retaining a result |
| Scoped lessons and human-input records | Original responses, conditions, reversible inference and dependent work | Private cross-chat retrieval with applicability/conflict review; concrete question batches and readiness notification |
| `factory.py` native input and operation preparation | Exact correction lineage and materialized producing context | Host adapters that demonstrate the context and image attachments actually reached the producing operation |
| Research admission, dispatch and closure | Bounded episodes, alternatives, counterlead and decision consumption | Evidence-linked child seeds, adaptive next-question selection and explicit reframing |
| Owned claims and reconciliation | Conflict checks; unknown effects block blind retries | Target-specific commit fencing, idempotency and cancellation acknowledgement where available |
| Full acceptance and delivery | Current objective, artifact/environment identity and fresh-consumer demonstration | A separate, nonterminal usable-release record for a named journey; full acceptance still covers all obligations |
| Project controls | Explicit drivers, observers, oracles and limits | Readiness runs against a real release, plus persistence and compatibility checks |
| Immutable skill installation | Reviewed source closure, discoverability, recovery and rollback | Qualify new adapters separately; preserve active task/release pins and native ownership |
| UI continuity module | Image-led exploration, reference nuance, fonts/icons and fresh critique | Qualified image transport, selected-design lineage, reusable component studies and actual rendered comparisons |

The existing code does not intercept arbitrary native actions. An environment
variable containing a context path does not prove a worker read it. A declared
dependency graph does not establish complete impact. A preview declaration is
not evidence of dependable use. The additions target these connections rather
than creating another source of truth.

The current text-only hosted worker adapter lists approved binary assets but
explicitly excludes them from visual model input. That restriction does not
apply to the normal native host. Use native Codex image access and generation.
From Claude, hand bounded image work to the installed Codex CLI, including
`codex --yolo` under the user's authorized permission policy. Pass the actual
reference files through supported image inputs, request generation through the
available image tool, and return generated artifacts for review and building.
Qualify actual inputs and outputs on that route; CLI help alone does not
demonstrate generation. Reuse these host capabilities without another image
service or a general-purpose transport framework.

Ordinary record appends require a single writer; the factory gate does not cover
every RDD append. Parallel workers submit results to the coordinator until all
participating append/snapshot paths share a qualified gate.

## Compare three complete approaches

These candidates pursue the same full product scope, early-use reliability and
reference fidelity. They differ in where execution authority lives.

| Candidate | Mechanism | Useful conditions | Cost and discriminating test |
| --- | --- | --- | --- |
| Native agent with a small project execution layer | Native agent chooses methods; existing journal binds actual operations, checks and releases | Default collaborative work; evolving tools and stronger models | Some native actions remain outside the owned boundary. Interrupt, correct and resume a complete journey; verify context use and remaining scope |
| Durable workflow runtime | Replayable orchestration, activities and explicit update/cancellation handling | Long unattended jobs, external effects, multiple processes or hosts needing durable coordination | Deployment, replay compatibility and effect adapters add cost. Kill workers around an external effect and show reconciliation without duplication |
| Incremental dataflow runtime | Track dependencies and recompute demanded affected results | Repeated analysis or generation with stable input relationships | Dynamic effects, unknown dependencies and sensory judgment are difficult to model. Change one source and demonstrate sound narrow revalidation, including an undeclared-impact case |

Recommended baseline: extend the native approach. Add durable execution or
incremental computation behind an adapter when a demonstrated project needs it.
The recommendation must be revisited if native interruption/recovery costs exceed
the qualified runtime's cost. Module boundaries do not require separate services,
repositories or mandatory infrastructure.

## One operation path, several evidence representations

The public interface remains an ordinary project request. The factory recovers
the goal, audience, normal entry/default state, hard constraints, preferences,
references, existing artifact and full completion obligations. It distinguishes
user intent from assistant proposals. A tentative example cannot silently become
the product scope or a universal preference.

At intake and consequential changes, retrieve relevant prior corrections from
accessible private conversations and project evidence. Keep source text, original
conditions and rationale, current fit, changed conditions, conflicts and reopen
triggers. Existing scoped lesson and human-input records carry the selected
evidence into this task; its journal remains authoritative for current decisions.
Explicit instructions retain their actual authority. Inferred preferences are
reversible interpretations and never supply missing authorization. Do not turn
local feedback into global policy or export private history with the package.

The native agent handles consequential ambiguity before expensive commitment:
obtain observable evidence, apply a fitting prior answer, use a disclosed
reversible assumption, or ask a concrete comparison that resolves downstream
choices. Bundle related questions and block only dependent work. Ordinary
technical choices remain the agent's responsibility. A repeated question needs a
changed condition, not simply a fresh chat that lost the earlier answer.

For consequential work, a producing operation consumes a bounded packet with:

- Current objective revision and applicable source-anchored requirements.
- Selected reference properties, conditions, minute differences and alternatives.
- Actual evidence needed for this operation, including readable images when visual.
- Affected components, dependency assumptions, expected effects and ownership.
- The proposed result and its claim-specific checks, reset and failure conditions.
- Known omissions, their reasons, and a route to reopen original evidence.

This extends existing records. It is not a universal language for every thought.
Visual pixels, interaction traces, source code, causal hypotheses and formal
models keep their appropriate representations. Short indexes locate the evidence;
they do not replace it. Models remain free to choose and revise methods within
the user's constraints and actual permissions.

An adapter declares its supported transports and guarantee boundary. A source
manifest and dispatch receipt establish what was supplied. A consuming-path test
establishes that the supported operation used it; neither establishes semantic
quality. Missing required evidence blocks that operation, while independent work
can continue. Reference content is untrusted evidence, not agent instructions.

## Research changes decisions, including their framing

The research engine extends existing episodes. A seed is an unresolved decision
with an underlying mechanism question, competing explanations, evidence that can
distinguish them, current feasible action and a bounded stop/reopen condition.
It need not be a repository name.

Inquiry, strategy and innovation can also be complete tasks. Their output is a
source-linked competing frame, actionable hypothesis, experiment or conditional
decision, with explicit limits and reopen conditions. Construction follows only
when authorized. Queryable discoveries do not create a permanent background job.

Each substantive layer must contain a parent finding, the new question it caused,
actual inspection, a finding with scope and counterevidence, and a consuming
decision or next seed. Ten independent searches are not ten recursive layers.
An explicit depth request is honored; normal use selects depth by uncertainty
and decision value. The process does not fabricate deeper questions when evidence
is inaccessible or no longer changes a decision.

At each step the agent can inspect code, acquire a missing state, test an
adaptation, seek a structurally distant mechanism, revisit the reference model,
or act using sufficient existing evidence. Reframing is an available action, not
the last step after repeated patches. When observations fit none of the initial
explanations, expand the candidate set instead of repeatedly reranking it.

Reference adoption records the useful mechanism, applicability, original and
adapted behavior, interaction with other adopted mechanisms, and a falsifier.
Keep small differences and conditional alternatives queryable. Retention does
not mean enabling every mechanism in every project. Shared mechanisms can have
one implementation while retaining distinct conditions and specialized variants.

Fresh handoffs have specific jobs:

1. A framer receives the user objective, raw relevant sources and observations,
   without the incumbent's preferred explanation. It proposes competing frames.
2. A specialist receives one consequential question, access boundary and required
   evidence; its conclusion must identify assumptions and a practical discriminator.
3. A builder receives the selected property, actual evidence and behavioral goal.
4. A critic receives the actual candidate and controlling references, without the
   builder's persuasive rationale. It reports localized failures and alternatives.
5. The native agent integrates results, resolves disagreement with evidence, and
   remains responsible for the full journey.

These are optional roles, not five agents required for every edit. Coherent work
stays together. New questions get fresh scoped contexts when that improves
independence or avoids inherited framing. Task independence does not prove model
diversity, ground truth or clean-room isolation.

An episode cannot close as useful adoption merely because its report cites a
source. Closure identifies the operation it changed: the next search question,
candidate selection, image prompt, builder input, checker or delivery decision.
If the useful result is a conditional alternative, retain its activation and
reversal conditions without forcing it into today's build. Method learning uses
actual outcomes and held-out replay; a model's praise of its own revised prompt
does not qualify a reusable improvement.

Preserve coverage and contrary evidence in question selection. Search rankings,
snippet summaries and a model's favored hypothesis can all suppress useful
mechanisms. Small-model routing, learned selection and automated prompt search
are conditional optimizations: compare whole-task results, missed candidates,
escalation and supervision costs before enabling them. Unknown billing or
unobserved native work remains unknown, rather than an invented saving.

## UI is a central production path

UI work has two simultaneous contracts: ordinary interaction competence and
selected visual character. A familiar task family requires actual conventional
behavior evidence; an attractive chat image does not establish streaming,
composition, cancellation, error recovery or scroll continuity. Add behaviors
only when they belong to the requested product.

### Explore with images

Start from inspected, well-made shipped products and human-designed references.
Establish provenance where possible; distinguish real UI from marketing art or
unverified authorship. Assign each reference a job such as density, navigation,
typography, motion, asset treatment or interaction. Preserve actual uploaded
pixels. Do not flatten nuanced images into a generic list of adjectives.

The chat agent frames purpose, representative content, semantics and essential
constraints. The image model explores composition, hierarchy and treatment.
Independent generations can reveal materially different interpretations; keep
exploration size proportional to the unresolved choice. When over-prescription
produces an unwanted result, change the next producing prompt and reference mix.
Do not answer by adding more arbitrary prohibitions.

Exploration and faithful reconstruction use different prompt modes. Open
ideation gets a brief and strong image inputs with room to interpret. A settled
design, reconstruction or localized repair gets precise relationships and
measured anchors. Evaluation can retain measurements that were deliberately not
prescribed during exploration. Freedom does not erase explicit user preferences.

### Form a system early, then implement precisely

For a new or materially revised visual language, use the early image loop to
discover a reusable system before extensive screen implementation. Study a
representative shell and contrasting component/content/state examples with strong
image inputs and a brief semantic goal. A whole screen is useful when it best
resolves hierarchy or navigation; it is not automatically the system for every
later screen. Explore materially different interpretations before narrowing.

Select the relationships that should persist: hierarchy, density, type, surfaces,
spacing, icons, motion and behavior. Keep system evidence distinct from a
screen-specific implementation target, including unresolved choices and permitted
local adaptations. Existing settled products retrieve their current system. This
step must not delay independent behavior or implementation work that can proceed
without choosing the visual direction.

Before selection, fresh critics inspect readable reference and candidate pixels,
the task, audience and controlling properties. They do not receive the preferred
verdict. Critique covers composition, reference nuance and task usefulness;
candidate-only review cannot qualify fidelity to unseen references. The native
agent inspects every candidate, resolves material disagreements, and requests
user judgment for consequential unresolved direction choices.

Record selected system studies and screen images with lineage, state/content,
viewport, deliberate adaptations and known flaws. Tokens support these
relationships; they cannot encode composition or replace the images.

Carry actual selected images and usable assets into image-to-code operations.
Check the image-producing and builder transports, not merely paths mentioned in
text. Verify CSS viewport and device scale, loaded font files and weights,
wrapping, pane ratios, control geometry and spacing in the rendered result.
Generated lettering is not proof of font identity. Use Geist by default and
Hugeicons Free Stroke Rounded. Never select Inter: this applies to image prompts,
builder handoffs, direct font imports, templates and fallbacks. Other reference-led
display faces remain available. A conflicting faithful-reconstruction request
must surface the conflict under the current hard constraint; only a later explicit
user instruction can change it. Inspect the actual rendered font, using a
browser-specific font-realization probe when available, alongside font assets,
weights and geometry.

Compare original references, selected image and coded render separately. A
generated design can already have drifted from the reference; faithfully coding
that drift does not recover the user's intent. Classify material differences as
intentional adaptation, unresolved substitution or implementation drift. Feed
localized findings and images into the next producing operation and repair drift
autonomously. Pixel differences and model scores locate concerns; they cannot
decide taste, utility or behavior alone.

### Extend and deliver the real experience

For settled changes, retrieve the chosen system and relevant component/state
examples; avoid inventing a new screen language on every turn. Use new image
studies when a meaningful question remains. Reusable stories and interaction
fixtures can carry realistic states into both component work and integrated
checks, with the actual application context restored for delivery.

Require fresh-context visual review of actual coded renders before consequential
visual delivery, with readable controlling references and selected design images.
Repeat it after material visual corrections. Require localized observations and
inspect the critic's evidence access. Scale the review to uncertain properties;
minor edits do not need a fixed panel. If fresh review is unavailable, record that
boundary rather than treating the builder's judgment as independent critique.
When the user's experience contradicts passing metrics, reconsider the objective,
comparison and evaluator before another cosmetic patch.

Readiness requires the complete ordinary journey, including actual content,
navigation, loading/error/empty states, persistence, responsive behavior and
recovery where relevant. A pleasing screenshot cannot conceal dead controls.
Visual and interaction contracts remain in force while later development runs.

## Dependable early use with continued construction

A usable release is a named complete journey and its dependency closure on a
pinned artifact, environment and data contract. It is a nonterminal record. It
lists what is usable, what remains unavailable, evidence of cold launch and
ordinary use, persistence/recovery checks, and compatibility with ongoing work.
The original full-scope obligation set remains visible and unchanged.

When readiness is established, show or open the exact qualified release and its
normal entry. Tell the user what is usable and what remains, then continue the
authorized work. Feedback from real use enters the same source-aware correction
path. A readiness record alone is not a user-visible handoff.

Build candidate changes separately from the stable artifact. Reuse worktrees and
the existing host before adding infrastructure. Parallelize independent work with
clear file/resource ownership; serialize shared effects. The development version
does not mutate a stable release or its data without a qualified transition.

Maintain a compact work frontier over full obligations, dependencies, ownership,
the early-use journey and the current integration or observation bottleneck. The
native agent selects feasible work by its likely contribution to dependable use
and full completion under the same quality target. Revise selection from actual
stalls, rework and integration cost. Keep capacity for integration; file-separated
fan-out alone does not establish behavioral independence or faster completion.

Immutable application versions do not make mutable data safe. Version the data
and API contract; use backward-compatible expansion/contraction where suitable,
validate migration and backup/restore behavior, and avoid promising rollback when
an older application cannot read newer data. A stable release may need an isolated
data snapshot or a deliberately compatible live store, depending on the product.

Promotion checks the current objective generation, expected release pointer,
candidate identity and readiness evidence at the actual target commit. Use
compare-and-swap or a target transaction where supported. A journal lock does not
fence an unrelated backend. For external effects, target idempotency and durable
reconciliation are needed; an outbox coordinates publication only inside its
stated transaction and delivery assumptions.

Corrections update source-anchored requirements and their affected decisions,
inputs and checks. Use narrow recomputation only when dependency coverage supports
it; unknown or newly discovered shared effects widen the affected scope. Preserve
unaffected evidence where justified. A still-usable older release can remain
available with truthful limits; a correction that makes its behavior unacceptable
revokes the affected readiness claim.

Stopping a producer does not prove its descendants or effects stopped. Record
unknown outcomes and reconcile before retrying. Resume uses exact current
objective/release/context identities, not a remembered plan. Native user input
and permission control remain authoritative; no automatic active-model switch or
duplicate Jev server is introduced.

## Proposed interfaces and transitions

These are design contracts to implement in the existing helpers and qualified
adapters, not currently available commands. Keep large evidence in captured
materials and use existing journal references rather than copying it into events.

| Operation | Required input and actual output | Admission or failure rule |
| --- | --- | --- |
| Bind/adopt intent | Existing native input plus exact source anchors, changed properties and adoption receipt | Preserve all root obligations; a correction is applied only when the affected producing decisions change |
| Retrieve prior intent / resolve ambiguity | Original private responses, conditions, current-fit decision, conflicts and question/assumption disposition | Inference cannot authorize an action; only applicable evidence enters this producer; dependent ambiguity waits |
| Compile/prepare work | Existing prepared operation plus operation-specific requirement generations, evidence projection, dependency/invariant/effect closure and coverage limits | Missing required evidence blocks; exact root obligations and lineage remain recoverable; qualified adapters demonstrate supported transport |
| Dispatch/close research | Existing episode plus parent finding refs, child question, inspected materials and consuming operation refs | Child must follow actual evidence; count inaccessible/failed inspections honestly; closure consumes a decision or retains a qualified deferred trigger |
| Submit/select a design | Image input hashes, actual attachment receipt, brief mode, candidate image/state identity, independent critique and selection revision | Unseen references cannot support a fidelity verdict; rejected or materially stale candidates cannot become a builder baseline |
| Verify a claim | Existing check records plus exact subject, property, checker version, assumptions and qualification scope | Pass applies only within the demonstrated scope; unavailable observations or negative-control failures prevent promotion authority |
| Propose usable release | Current objective, named journey, dependency/invariant closure, build/runtime/data identities, checks, fresh use and remaining obligations | Readiness fails if active work can affect the closure without qualified isolation; full acceptance remains separate |
| Hand off dependable use | Qualified release identity, launch/open result, truthful usable scope and continuing work frontier | A declared preview or unopened artifact does not establish the user received the usable release |
| Promote/reconcile release | Existing owned operation plus expected stable descriptor, current authority epoch, target receipt and observed served identity | Target checks freshness/idempotency at effect; a lost reply stays unknown and blocks conflicting retry until reconciled |
| Resume/stop | Root, immutable package/interpreter/adapter pins, latest intent, pending effect records and stable entry | Resolve stale authority and in-flight effects before new mutations; stopping development does not erase personal data |

The native adapter reports prepared, dispatched, returned, observed and accepted
states separately. For a candidate, the release path is:

```text
building → candidate → qualified journey → promoted usable release
                ↘ failed / stale / unresolved → diagnose or reconcile
```

Full completion is a separate root state reached only after all original current
obligations pass acceptance. New unrelated work may continue during usable-release
promotion; shared invariants and data remain part of its protected closure.

Correction processing has a critical ordering boundary: capture the source,
advance or revoke relevant target authority, determine impact, then admit new
work. If a host cannot connect user corrections to that boundary before external
effects, it must declare stale-effect exclusion unsupported. An append-only
correction event alone cannot repair that race. Concrete project adapters choose
the achievable transaction, conditional-write or observation protocol.

Implement selective authority in `compile`, `prepare_owned_operation`,
`_validate_operation` and `rebase_operation`, rather than relaxing today's whole-root
checks. Bind the operation to its relevant property generations and inspected
consumer/effect coverage while retaining the full root obligation set. Declared
file mappings alone cannot establish every semantic consumer; unexamined or newly
discovered coupling widens revalidation. Final acceptance still uses the current
full denominator.

Checker qualification binds checker code/version, subject class, property,
assumptions and negative-control scope. Readiness and final acceptance consume
that qualification; different producer/checker labels alone do not establish it.
Reconciliation adapters observe the actual target's operation identity, payload,
data contract and consistency boundary. A pending task binds immutable package,
interpreter and adapter identities; discovery through a mutable symlink does not
establish which interpreter resumes it.

## Verification and the custom-language decision

Choose checks by claim, not by prestige. Behavioral journeys, differential tests,
property-based tests, fault injection, model checking and proof can complement
visual judgment. Preserve checker identity, exact subject, assumptions, coverage,
and failure evidence. Include realistic negative controls before a checker can
authorize its intended class of result.

Formal evidence needs two bridges: user intent to specification, and specification
to actual implementation/environment. Review the theorem statement and transitive
definitions; reject forbidden assumptions. Audit trace parsing, identities,
ordering and omitted events. A proven abstract model or verified contract does
not by itself establish the deployed program. Sensory quality still requires
artifact and user judgment.

Separate execution runtime, semantic representation and checker choice. Lean can
provide executable specifications as well as proofs. TLA+/P model transitions;
MLIR offers typed operations and staged lowerings; XLA targets numerical programs.
These are useful mechanisms, not a ready-made meaning for arbitrary product
intent. Define the factory's narrow transition semantics independently of their
JSON serialization before choosing a surface syntax.

Compare three representation candidates on correction versus release promotion:
existing typed records with an explicit interpreter, a Lean-embedded executable
model, and a restricted custom representation with qualified lowerings. Check
rejected invalid states, model/implementation mismatch, maintenance cost and
backend portability. Keep images, assets, observations and behavior evidence as
referenced operands; do not flatten them all into prose or logic. The initial
implementation should extend existing records and adapters, with checker-specific
exports. No new general-purpose language is justified merely to rename the
journal or make prompts look formal.

A custom language has a stronger case if repeated operations need independently
specified semantics, static checking and multiple interchangeable backends that
existing schemas/libraries cannot express without recurring errors. Demonstrate
that on real tasks first. A restricted declarative policy or workflow notation
may then be useful; its compiler/runtime/tests and escape hatches become additional
trust boundaries. It would orchestrate qualified tools, not replace their proof
kernels or invent a universal product-quality oracle.

Strict clean-room reconstruction keeps analyst source access separate from the
builder's allowed behavioral exports through enforced access boundaries. Fresh
context and a separate folder do not establish isolation. Public releases must
also preserve code/asset rights and attribution. Permission to inspect a reference
does not automatically authorize its source, assets or private captures for reuse.
Owned clean-room dispatch binds a reviewed builder projection and isolation
receipt, while the coordinator retains a separate analyst authority manifest.
Do not remove the current analyst-capsule blocker or give that capsule to the
builder merely to make ordinary dispatch work.

## Construct and qualify the integrated system

Implement the full connective path over current helpers: source-aware intake,
operation-specific evidence transport, adaptive research, visual generation and
render checks, owned execution, correction/recovery, nonterminal readiness and
continued full-scope completion. Staging construction tests dependencies without
redefining the requested system as an MVP. Unqualified optimizers run in shadow;
they cannot claim authority because their schemas validate.

Begin with one complete representative project journey and explicit observation:
normal request → reference discovery and selected direction → producing operation
→ real artifact → fresh cold use → continued independent development → correction
→ interruption/resume → final full acceptance. Exercise a visual disagreement,
stale result, omitted dependency, data migration, lost effect reply and negative
checker candidate. Preserve the normal entry and default state throughout.

Qualification compares native-agent work, the current factory and the integrated
candidate on equivalent complete tasks with equal evidence access and resource
ceilings. Use held-out tasks and corrections, multiple outcomes and independent
judgment. Evaluate time to first dependable use, final fidelity/functionality,
full completion time, total cost including research/review/retries/integration,
repeat corrections and human supervision. Do not reward early readiness by
shrinking scope or accepting lower quality. Trace which mechanism changed the
producing operation and outcome; retire cost without demonstrated benefit while
preserving the underlying evidence and alternative.

Distribution remains a portable skill plus local helpers and optional adapters.
Install only reviewed source closures; validate cold discovery, actual invocation,
context application and representative use separately. Keep project state separate
from immutable package releases. Package rollback is not data rollback. New host
or domain integrations declare capabilities, unavailable operations and recovery
limits. Publish generic mechanisms and authored fixtures; private research,
captures, credentials and project narratives remain outside the repository.

The architecture is supported by source inspection, not a measured claim that
this integrated factory outperforms the current one. The implementation and
comparative complete-journey qualification remain to be done.
