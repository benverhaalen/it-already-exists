# Worked example: transfer expert judgment without automatic skill creation

Synthetic proposed case, not a benchmark or a demonstrated product improvement.

A user asks the existing coding agent to improve an inspiration library's collection-and-editor experience. The agent enters through the normal project workflow and identifies a consequential uncertainty: useful motion and credible verification of long titles, empty content, interrupted editing, and failed saves.

The agent uses product references for the desired behavior and expert-process references for how to inspect and improve it. It studies the relevant branches of Emil Kowalski's animation and break-ui guidance, and pstack's verification construction process. Source prescriptions are documented evidence; effectiveness in this project remains to be tested.

The contributions remain distinct: deciding whether motion is warranted; choosing motion origin by interaction; probing extreme data at the real input boundary; checking action/result/side effects; and preserving proof while cleaning up fixtures. Their source links, exceptions, and alternatives remain recoverable even when only some are active.

The current implementation assignment includes conditional judgment: evaluate repeated interactions before adding animation; anchor a popover to its trigger; test cancellation mid-transition; derive plausible longest titles and missing values from the project's actual schema and data ingress; exercise open/select/edit/invalid input/correct/save/navigate/return, with delayed and failed saves. Inspect rendered results and durable state. Record limits for inaccessible states. This example does not prescribe universal motion durations or invent unsupported data bounds.

The carrier is a focused task prompt plus project-local references and existing verification tools. No new skill is necessary for a single investigation. If future tasks repeatedly need the same review judgment, propose a small skill with an appropriate trigger. If fixture setup and state checks are repeated and deterministic, implement a tool and test its cleanup and failure behavior. A scheduled improvement loop would require a separately authorized runtime and actual feedback path.

Check against the original project outcome: did users retain control, could they recover after failure, and did the useful properties survive the full journey? For a consequential method claim, compare the ordinary workflow with the extracted prompt on matched tasks, retaining contrary cases and total costs. Compare reusable packaging only when claiming that reuse adds value. Passing journal validation establishes provenance structure, not these outcomes.

If strict clean-room access is selected, the analyst exports reviewed observable requirements and checks through the existing verified boundary. The implementer does not receive the upstream source instructions or this source-bearing research history.
