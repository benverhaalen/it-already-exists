# Preserve competence and character when combining UI references

Use for UI adaptation, reconstruction, extension and repair. Recover the operation and selected product language first. A missing design document does not make a working app greenfield; a local specimen is not automatically a replacement screen. User references carry property-specific authority, not blanket approval.

## UI font and icon defaults

Use Geist Sans for utility text and the default sans-serif face. Do not select Inter, including through a component template, font import or fallback stack. Preserve expressive reference-led display typography when it serves the chosen direction; using Geist for controls does not make every heading sans-serif. Put these choices into image-generation prompts and builder handoffs, and verify the real font asset loaded in the coded result.

Default to Hugeicons' free Stroke Rounded family unless the user states otherwise. Use `@hugeicons/core-free-icons` with a framework-appropriate renderer. A provisional desktop treatment is 18px with stroke width 1.35. Treat that as a useful starting size, then inspect legibility at the actual component scale. Use official icon data and a framework-appropriate renderer, keep semantic mappings consistent, and preserve license notices. Provider logos remain separate assets. Do not substitute Lucide or hand-drawn lookalikes merely because a template supplies them. For a faithful reconstruction that requires a conflicting font or icon identity, surface the conflict before adopting it.

These defaults are explicit user preferences for this workflow, not findings that Geist or Hugeicons universally produces better design.

## Two simultaneous contracts

`competence` describes the expected task behavior, semantics, data boundary and ordinary interaction conventions. `character` describes the selected hierarchy, density, composition, typography, assets and motion relationships. Neither replaces the other. Encode both in the task contract as property/authority/preserve/adapt/check items. Resolve conflicts before passing them to a builder; contracts must agree about what the user can do and what can change.

First recognize the task family and inspect relevant conventional mechanisms. In conversational products, inspect streaming/pending/error states, cancellation, draft retention, IME composition, attachments, scroll anchoring, jump-to-latest, tool results/approval and return continuity where offered. These are investigation handles, not a requirement to add every feature. Other families have their own conventions: selection and undo in editors, query/filter continuity in search, recurrence/time zones in calendars. Acquire actual supporting references rather than assume visual familiarity supplies correct behavior.

Combine references by their job. One can establish navigation, another content density, another motion, another recovery. Preserve each source's invariant, permitted adaptation, failure boundary and minute distinction. Do not average incompatible systems into incoherent defaults. Keep conditional specialists and rejected alternatives in the journal. Explicit audience/product decisions outrank generic taste prescriptions; an expert skill supplies cues and exceptions, not unconditional authority.

## Make the selected language operational

### Image-led direction and faithful implementation

For visually consequential UI work, default to inspected, well-made shipped products and human-designed sites as visual anchors, with image-to-code as the main construction method. Prefer actual product screens over AI concept galleries. Establish provenance and distinguish observed product UI from marketing illustrations or an unverified claim of human authorship. Assign each reference a property to transfer; a market interface may supply density without supplying the navigation of a notes app.

Let the image model develop visual composition from the actual references, task, audience, representative content and essential constraints. The chat model frames semantics, behavior, accessibility and compatibility; it should not preempt visual exploration with arbitrary font bans, tiny-accent rules or a fully prescribed layout. Explicit user choices and a settled product language remain controlling. Use available image-to-code capabilities often for new surfaces and consequential changes; reuse an applicable selected image for settled changes instead of regenerating every edit. If image generation is unavailable, state the limitation and implement from inspected reference pixels rather than claiming an image-led process ran.

Verify the image handoff in the producing call: attach the actual image inputs through the tool's supported fields. Filenames written in prompt text are not image inputs. Inspect local images before sending them, ensure legibility, and record which inputs and generation produced a candidate. For strict clean-room work, supply only permitted visual/behavioral evidence, never source or implementation-bearing material.

For a working product where component familiarity, font identity or laptop density matters, anchor those properties before generation. Inspect real component source or a rendered component study; record intended CSS viewport, control heights, utility type sizes, pane relationships and font files/weights actually available. Attach readable component/reference pixels and give these measured constraints to the image-producing call. An output raster's dimensions or a “MacBook screenshot” prompt does not establish CSS scale, device pixel ratio or usable density. Image models can develop composition and atmosphere around the anchors; they need not invent every control. Do not claim an exact typeface match from generated lettering or a font name in an image. Verify font identity in source/assets where accessible; mark alternatives as deliberate substitutions and check their actual rendered metrics. If the candidate violates an important anchor, repair or reject it before treating it as a build baseline. Compact desktop and comfortable touch targets can coexist; shadcn metrics are one inspected option, not a universal template.

Translate the user's reference intent at the property level before prompting: which visible relationships matter, which examples are weak signals, and which incidental features do not transfer? Briefly surface consequential interpretations. For example, a marketing screenshot can supply editorial letterforms, weight contrast and surface warmth without supplying a working editor's density or navigation. Give the actual uploaded images most of the visual burden; text identifies their jobs, conflicts and task constraints instead of paraphrasing them into a generic “premium” style. Preserve the subtle property being requested: compact controls do not imply removing expressive typography, and a serif/sans pairing does not imply applying serif to every label. If a correction removes another desired property, revisit the transfer rather than treating the tradeoff as inevitable.

Select a coherent candidate and preserve its lineage. Selection may be provisional agent judgment within settled intent; involve the user at consequential direction choices, not for routine pixel corrections. Record the chosen screen/state/breakpoint, its controlling properties, known flaws and deliberate adaptations. Carry the image itself, usable assets, font/icon identity, composition relationships and relevant behavior into the builder's context. Tokens support this handoff but cannot replace it. A matching palette with different type, shell geometry or hierarchy is drift.

Extend the selected language through a component or screen study in the existing shell when that is the unresolved question. For familiar task families, inspect real conventional interfaces as well as generating a polished image: an attractive chat mockup does not establish composer expansion, streaming, cancellation or scroll behavior. Inspect the coded result at representative sizes and states against the selected image before presenting it. Correct obvious visual mismatches autonomously; do not make the user repeat settled choices. Compare the complete journey separately so visual approval cannot conceal dead controls, failed persistence or broken recovery. Compare the reference and real rendered state side by side at identified dimensions. Check pane ratios and alignment, type shape/weight/size/wrapping, control geometry, spacing relationships and asset treatment separately. Classify each material mismatch as intended adaptation, unresolved substitution or implementation drift; repair drift rather than silently accepting “inspired by.” Carry actual images and these localized differences into the next producing operation. A raster is insufficient to identify an exact font or interactive state: acquire usable assets and behavior evidence for those properties. When a generated candidate itself departs from the user's references, do not faithfully code that departure and call the transfer successful.

Common transfer failures include naming image paths without attaching pixels, prescribing the entire composition before exploration, and accepting visual drift without inspecting the coded result. Put the correction into the actual generation and implementation calls. A model or skill choice alone does not establish quality; corrected instructions do not prove earlier execution.

Use examples and counterexamples to describe relationships that tokens cannot encode. Typed tokens/aliases can carry values; constraints carry composition; state fixtures and semantic actions carry behavior. Approved examples need task, build, viewport, state/data and decision identity. Reuse actual structured assets when their rights and evidence fit; generated imagery is for unresolved direction, not proof of exact typography or behavior.

Choose exploration size by uncertainty. A local motion or component question can use a small study placed in the selected shell. Navigation, density or hierarchy can require a full screen/flow study. Do not generate a whole redesign for an already settled component change. Preserve real data boundaries and plausible extreme content in later evaluation; mocked examples alone cannot establish integration.

A comparison contract must identify reference and candidate build/state/fixture/viewport/environment/decision version, intended fidelity versus adaptation, eligible baseline, known defects and permitted changes. Compare structure, appearance, behavior, timing, semantics and usefulness separately. An old rejected baseline cannot overrule a newly selected direction. Preserve reference defects as observations; classify emulator overlays and capture damage before adopting them.

For consequential image-led UI work, use fresh-context visual critique before adopting a generated image as a build baseline, after a revision that changes an important reference property, and on the actual coded result before delivery. Inspect every candidate yourself; use independent agents where available for those consequential decisions rather than sending every minor edit through a fixed panel. If independent review is unavailable, disclose that limitation. Scale the review to unresolved questions: separate reference nuance from component/interaction competence when these need different evidence. Give each critic the actual readable reference and candidate images, goal, audience, property authority and constraints, without the builder's persuasive rationale or expected verdict. A fresh worker's label alone does not establish independence; verify its evidence access and actual output.

Require localized observations and an accept/revise/reject recommendation with reasons. Inspect and reconcile critiques yourself; agreement is not a quality certificate and disagreement should prompt a discriminating comparison. Bind the retained review to candidate identity and reference version, record which findings changed the next producing prompt or implementation, and show the repaired artifact to a fresh critic when a material defect was identified. Do not code a rejected generation merely because it is attractive or already exists. Localized concerns are hypotheses until checked against the pixels, actual geometry or behavior; when feedback contradicts metrics, inspect the objective, baseline and evaluator before another cosmetic patch.

## Image generation as ideation

Images can discover a product interpretation, not only render a design already
decided in chat. When the user wants exploration, start with the actual reference
images, a short statement of the product's purpose and explicit hard preferences.
Let the image model choose composition, hierarchy, palette and component
treatment. Do not translate every reference into prescribed rows, panes, pixel
values and negative instructions before giving it a chance to interpret them.
Reserve detailed measured prompts for faithful reconstruction, a settled build
baseline or a localized repair. Keep needed measurements for later evaluation;
they need not all become instructions in an exploratory producing call.

Use multiple independent images when uncertainty makes the differences useful.
An identical brief can reveal alternate interpretations; a small change of brief
or reference set can test a particular question. Choose the breadth for the
unresolved decision rather than a fixed quota. Inspect what each image proposes
about the product: what the user recognizes, what the primary task becomes,
what deserves space, and what information supports the next action. Compare
tradeoffs and promising ideas, not just which image is prettiest. Give fresh
critics the actual candidate images and their source references without the
favored interpretation. A candidate-only review can judge usefulness and
composition, but cannot qualify fidelity to an unseen reference. Distinguish
an interface concept, an annotated explanation of a reference, and a moodboard;
each may reveal useful ideas, but only the interface concept specifies a screen
to implement. Compare different moments in the same user journey when a single
screen hides an unresolved product decision.

Keep discovered features as proposals. Invented counts, quotes, previews,
source attributions and interaction states are not facts or functioning
capabilities. Evaluate whether a useful proposal fits the intended product,
has evidence and assets, and merits implementation; do not automatically reject
it for exceeding today's specimen, or automatically ship every generated
control. Combine mechanisms that serve a coherent journey rather than piling
all attractive elements into one screen. Generate another image when it can
resolve a consequential uncertainty, then move a selected direction into the
precise image-to-code and interaction verification process.

If the user reports over-prescription or an AI-looking result, change the next
generation operation, not merely the saved principle. Preserve the prompts,
attached inputs, output identities and review so the comparison is inspectable.
One freer sample does not establish what caused an improvement: content richness,
scale, scope and layout can change together. User feedback controls the desired
direction even when metrics pass.

## Source-informed contributions and limits

These references were inspected in the research that informed this module. The methods index turns them into conditional candidates; original expression and code have not been copied here.

- [assistant-ui](https://github.com/assistant-ui/assistant-ui/tree/0bdf05066fcb83a64a07d542dde4fea0e8f99b76), MIT: reader-position-aware scroll behavior and distinct run/thread transitions. [AI Elements](https://github.com/vercel/ai-elements/tree/6a9d5b1822ffb10bba4bd97175f01edd7d8651cd), Apache-2.0: composition-aware submit, failure retention and conversation controls. Primitives do not supply a correct backend or all chat behaviors.
- [Impeccable](https://github.com/pbakaus/impeccable/tree/6e802bd0ed99f53180e2359fddab6da8d97970d9), Apache-2.0: operation-aware refinement and judgment before detector evidence. [Emil's skills](https://github.com/emilkowalski/skills/tree/e8a175de22ae1e49370fc144c1f3bb9aeedf988d), MIT: cue-based motion opportunity diagnosis separate from recipes. Neither establishes universal taste or universal timing rules.
- [Superdesign skill](https://github.com/superdesigndev/superdesign-skill/tree/f9f05cd988c247dce6c072eaf9ac6b162f2ffc4b), MIT: selected-context and draft lineage with fingerprints. Hosted generation engine is separate. [UI UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/tree/477bcb28c9812b385cb51a4605ddf30d7b2266e2), MIT: retrieval diagnostics and abstention; lexical scores cannot supply missing knowledge or override explicit decisions.
- [Argos](https://github.com/argos-ci/argos/tree/be8f2ad78a79ae97101337fb0d658f69ae4b23f5), MIT: eligible comparison identities. [Playwright snapshots](https://playwright.dev/docs/test-snapshots): stabilized captures and environment sensitivity. [pixelmatch](https://github.com/mapbox/pixelmatch/tree/b2800051f2b79d18cf27e51cd240cafd38cfb0ba), ISC: localized image differences. None alone establishes usable or faithful behavior; masks and normalized images can conceal important errors.
- [Storybook portable stories](https://storybook.js.org/docs/writing-tests/integrations/stories-in-unit-tests): reusable configured state and interaction examples. [DTCG 2025.10](https://www.w3.org/community/reports/design-tokens/CG-FINAL-format-20251028/) and [Style Dictionary](https://styledictionary.com/info/tokens/): typed values, aliases and origin metadata. Token systems need composition and behavioral contracts alongside them.
- [UICrit](https://arxiv.org/html/2407.08850v3): task-conditioned examples and localized critique in a bounded mobile study. Dataset CC BY 4.0, upstream image rights separate; current-model generalization not established. [Design2Code](https://github.com/NoviScl/Design2Code): decomposed visual signals; README research-use restrictions require exact rights review. [DesignBench](https://github.com/WebPAI/DesignBench/tree/a1e58d66ecbf1f77848bc5529ee7bbbe33bc25ba): separate generation/edit/repair tasks; no root license found in inspection and dimension-mismatch random preprocessing needs scrutiny before reuse.

October 3–4 snapshots are current October research, not proof of September availability. Recheck exact licenses/revisions before dependency or expression reuse. Stronger and weaker prior project outcomes motivated these questions; retrospective differences do not prove which individual skill caused success or failure. This module's effectiveness remains for user-chosen evaluation.
