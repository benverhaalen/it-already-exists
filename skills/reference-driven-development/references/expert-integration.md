## Apply across domains

For a selected expert contribution, identify its cue, required evidence, action, exception, and discriminating check. Preserve adjacent distinctions rather than compressing everything into “research, build, review.” Use the methods index for retrieval, then inspect the original source if the summary cannot settle a decision.

- Feedback: define the intended property, observation channel, decision rule, producing operation, disturbances and stop/revisit condition in the transfer. Return concrete counterexamples to the next operation. Keep one-off preferences separate from shared factual corrections.
- Corrections: inspect whether an existing check exists but is not called. Prefer repairing that path over adding another tool. If the mistake is deterministic, use a type, schema, shared primitive or executable check; if contextual, use a scoped judgment rule with exceptions. Record actual enforcement evidence in a check; lesson receipt is insufficient.
- Context: recover evidence using exact project and decision scope. Keep raw history retrievable outside active context. A summary is navigation, not authoritative current state. Avoid fixed time windows that omit a relevant older decision.
- Verification: derive an adapter from the real launch, input, observation and cleanup boundaries. Do not fabricate robustness by editing the component under test. Preserve evidence before cleanup. Future real-case evaluation must inspect sensory results and full user journeys.
- Domain language: preserve distinctions needed by the user journey before selecting data structures. Check terms against observed behavior and actual code; do not force the user to adjudicate contradictions the agent can investigate.

## Cheap code changes the research method

Use modern agentic code generation to make inspectable alternatives and small discriminating probes inexpensive. Choose the uncertainty first: interface shape, hidden state, visual hierarchy, integration feasibility or another concrete question. Define competing expected observations, bounded inputs, a reproducible launch/reset recipe and the evidence to retain before writing the probe.

A disposable probe may deliberately omit production abstractions, but must support its stated observation. Keep its verdict and source identity recoverable even if the code is removed. Cheap generation favors replacing a weak sketch rather than defending sunk effort; it does not make evaluation, reference acquisition, integration or human review free. Measure those separately. Promote supported mechanisms into production with the necessary failure handling and integration checks; a throwaway result cannot certify production quality.

Treat OSS as a library of mechanisms and discriminating examples, rather than a ceiling on available tooling. Agents can write parsers, capture adapters, normalizers, candidate renderers and language bindings when an existing tool does not fit. Choose the language by runtime access, libraries, latency, maintainability and distribution; do not preserve an accidental language boundary merely because a reference used it. Code generation and refactoring costs remain empirical, particularly at integration boundaries.

For a substantial rewrite, pin the prior artifact, intended behavioral contracts and independent comparison evidence before changing implementation structure or language. Separate semantic repair from structural refactoring when doing so makes discrepancies easier to localize. Qualify a bounded transformed slice under the same inputs, histories and measurement conditions; retain numerical precision, clocks, persistence, ordering, errors and platform conventions as separate obligations. Extend the rewrite after that slice provides useful evidence without shrinking the full goal. An agent's new test derived from its own implementation is weaker than an independently grounded oracle. Compilation, idiomatic code and cleaner architecture do not by themselves demonstrate equivalence.

Inspected [C2Rust guidance](https://github.com/immunant/c2rust) illustrates a useful staging mechanism: preserve low-level behavior during translation before progressively refactoring, with cross-checking where available. Its scope is C-to-Rust, not arbitrary platform migration. [Alive2](https://github.com/AliveToolkit/alive2) is a conditional LLVM translation-validation reference for bounded transformations; it does not certify application journeys or UI fidelity. These sources were consulted in October; no new September availability claim or measured benefit is made. Recheck exact revisions and licenses before reuse.

Keep analyst tooling and product construction separate in strict mode. The analyst may build tools around permitted original evidence; independent implementers receive reviewed behavior and permitted assets. Rewriting decompiled reference code into another language remains source-derived implementation. Cheap code should expand useful experimentation and implementation choices while preserving this boundary.

Use different constraints when exploring alternatives so several versions teach something. More variants or agents are valuable only while they resolve consequential uncertainty. Do not shrink the requested product to the probe. During development of this package, real reconstruction probes are deferred to user-selected examples; only synthetic mechanics and source-informed critical review are used.

## Additional assurance references

[TesterArmy e2e](https://github.com/tester-army/e2e/tree/f99e80ebc04f8194f967244198783db871390e06) (October 4, Apache-2.0 observed) was inspected through README, cache documentation, cache/decide.ts and selected agent/step-cache.ts. It mixes deterministic assertions with agent actions and separates replay eligibility from live verdicts. Transfer: cache qualified actions with explicit identity, starting conditions and later outcome verification; stop or hand off on ambiguous targets or changed state. Keep assertions live. Replay evidence covers observed controls and effects, not complete behavioral equivalence. This is an adapter candidate, not an installed or benchmarked integration. The [requested page](https://tester.army/e2e) links the source and Markdown docs.

Adapt policy to the target language and preserve local customizations during updates. This repository's Python helpers need Python boundary validation, not an unrelated Oxlint installation. A justification comment is a review cue, not proof that an assertion is safe.
